# Чаты турниров — дизайн

**Дата:** 2026-07-01
**Статус:** утверждён (brainstorming), готов к плану реализации
**Область:** Flutter-приложение `padel_app` + бэкенд Laravel (`padel`, `https://padel-p.kz/api/mobile`)

## 1. Цель

Внутри каждого турнира — чат для общения участников и организатора. Организатор
(админ клуба) при создании турнира выбирает, кто может писать. Кнопка чата с
бейджем непрочитанных живёт на экране турнира. Реалтайм без веб-сокетов —
через опрос (polling) при открытии экрана чата.

Первый этап — **только текст**. Фото/файлы, жалобы, реакции — потом.

## 2. Модель прав (сервер-центричная)

Клиент **не вычисляет права сам**. Бэкенд на каждый турнир отдаёт готовые
capabilities — это исключает рассинхрон логики между фронтом и бэком.

Три режима записи (`write_mode`), задаются тумблером при создании турнира:

| Режим | Кто пишет | Кто читает (видит чат) |
|---|---|---|
| `admin` | только организатор | организатор + участники турнира |
| `participants` (по умолчанию) | организатор + участники | организатор + участники |
| `everyone` | любой, кто видит турнир | любой, кто видит турнир |

Правила:
- **Чтение = принадлежность к аудитории режима.** Спектатор (не записан) видит
  чат только в режиме `everyone`.
- Режим `admin` — доска объявлений: участники читают в режиме read-only.
- **«Админ»** = пользователь, управляющий клубом турнира (`User.adminClubs` /
  `moderatorClubs` → геттер `manageableClubs`, проверяется по `tournament.club.id`).
  Итоговое право приходит с сервера как `is_admin`.
- После завершения турнира (`status == 'completed'`) — `can_write = false`,
  `can_read` остаётся → режим read-only.
- Организатор может выключить чат на турнире целиком (`enabled = false`) —
  тогда кнопки чата нет.

## 3. Контракт API

### 3.1. Блок `chat` в существующих ответах

Добавляется в `GET /tournaments/{id}` и в карточку турнира в списках
(`GET /tournaments`, `/tournaments/my` и т.п. — там достаточно `enabled`,
`can_read`, `unread_count` для бейджа):

```jsonc
"chat": {
  "enabled": true,              // включён ли чат у турнира
  "write_mode": "participants", // admin | participants | everyone
  "can_read": true,             // показывать ли кнопку/экран чата
  "can_write": true,            // может ли текущий юзер писать сейчас
  "is_admin": false,            // может ли удалять любые сообщения
  "unread_count": 3             // непрочитанные для бейджа
}
```

### 3.2. Модель сообщения

```jsonc
{
  "id": 123,
  "user": { "id": 7, "name": "Иван Петров", "avatar": "https://…", "level": "3.5" },
  "text": "Кто на 19:00?",
  "is_admin": true,   // автор — организатор (бейдж «Организатор», акцентный стиль)
  "is_mine": false,   // моё сообщение (выравнивание справа)
  "created_at": "2026-07-01T12:00:00Z"
}
```

### 3.3. Эндпоинты

```
GET    /tournaments/{id}/chat/messages?after_id=&before_id=&limit=50
POST   /tournaments/{id}/chat/messages          body: { "text": "…" }
DELETE /tournaments/{id}/chat/messages/{msgId}
POST   /tournaments/{id}/chat/read              body: { "last_message_id": 123 }
```

- `GET messages` без параметров → последние ~50 (по убыванию `created_at`,
  клиент разворачивает). `before_id` — история вверх (пагинация). `after_id` —
  только новые (для опроса и pull-to-refresh, дёшево).
- Сервер — источник правды по правам: `POST` при `can_write=false` → **403**;
  `DELETE` чужого сообщения без прав админа → **403**.
- Пустой/слишком длинный `text` → **422** (лимит длины задаёт бэкенд, напр. 2000).

### 3.4. Непрочитанное

- Бэкенд хранит на каждого юзера `last_read_message_id` для турнира.
- `unread_count` = число сообщений с `id > last_read_message_id` (сообщения
  самого юзера не считаются непрочитанными).
- `POST .../read` с id последнего видимого сообщения при открытом чате →
  бейдж обнуляется.

## 4. Опрос (polling) — без веб-сокетов

1. **При открытии турнира** — `unread_count` уже приходит в `GET /tournaments/{id}`,
   отдельный запрос не нужен → рисуем бейдж на кнопке чата.
2. **Внутри экрана чата** — таймер каждые ~5 сек: `GET .../messages?after_id=<последний>`
   → дописываем новые снизу; сразу `POST .../read`.
3. **Pull-to-refresh** (потянуть вниз) — тот же запрос вручную.
4. Таймер работает **только пока экран чата на переднем плане** — стоп в
   `dispose()` и при уходе в фон (`AppLifecycleState`), чтобы не грузить сервер.

**Ошибки сети:**
- Отправка не прошла → сообщение помечается «не отправлено», кнопка «повторить»,
  уведомление через `showAppAlert` (не SnackBar — правило проекта).
- Опрос молча ретраит на следующем тике.

## 5. Модерация (этап 1)

- **Админ** удаляет любое сообщение.
- **Обычный юзер** удаляет только своё.
- UI: long-press на сообщении → bottom sheet / `showAppAlert` с «Удалить»,
  пункт виден только если `is_mine` или `chat.is_admin`.
- Сервер перепроверяет право (см. 403 выше).
- Удалённое сообщение исчезает из ленты (жёсткое удаление; «сообщение удалено»-
  плейсхолдер — потом, если понадобится).

## 6. UI и точки интеграции

### 6.1. Кнопка чата на экране турнира — `tournament_detail_screen.dart`
- В шапке рядом (слева) с существующей круглой кнопкой share (`ios_share`) —
  такая же круглая 40×40 кнопка, иконка `Icons.chat_bubble_outline`.
- Бейдж непрочитанных: кружок accent-цвета с числом в правом-верхнем углу
  (стиль `_buildCountBadge`, уже есть в проекте). `unread_count == 0` → без бейджа.
- Кнопка видна только при `chat.can_read == true`.

### 6.2. Экран чата — новый `screens/tournament_chat_screen.dart`
- Шапка: круглая `AppBackButton` (правило проекта) + название турнира +
  подпись-режим («Только организатор» / «Участники» / «Открытый чат»).
- Лента: свои сообщения справа (accent-пузырь), чужие слева (card-пузырь) с
  аватаром, именем, уровнем. Сообщения админа — бейдж «Организатор» + акцентный
  ник. Стиль переиспользуем из support-чата (`support_ticket_thread_screen.dart`).
- Ввод внизу: поле + кнопка отправки. При `can_write == false` — вместо поля
  серая плашка: «Писать может только организатор» либо «Чат завершён — только
  чтение».
- Pull-to-refresh сверху; автоскролл вниз при своих новых сообщениях.

### 6.3. Настройка режима при создании — `admin_create_tournament_screen.dart`
- В ряд к `_ratingToggle` / `_verifiedToggle` добавить блок «Чат турнира»:
  - тумблер «Включить чат» (`enabled`);
  - сегмент-переключатель из 3 значений: Только организатор / Участники / Все
    (по умолчанию — **Участники**) + пояснение под ним.
- Тот же блок в редактировании турнира — менять после создания.
- Admin-экраны: строки можно хардкодить (как в остальной админке).

### 6.4. Локализация
- Все пользовательские строки чата — через `AppLocalizations` (**RU + EN + KK**),
  правило проекта. Хардкод запрещён (кроме admin-экрана создания).

## 7. Раскладка по файлам (по текущей структуре)

**Flutter:**
- `models/chat_message.dart` — сообщение.
- `models/tournament_chat.dart` — блок `chat` (парсится в `Tournament`).
- `services/chat_service.dart` — 4 эндпоинта.
- `providers/chat_provider.dart` — список сообщений, опрос-таймер, отправка,
  удаление, unread; жизненный цикл таймера.
- `screens/tournament_chat_screen.dart` — экран.
- Правки: `models/tournament.dart` (поле `chat`), `tournament_detail_screen.dart`
  (кнопка+бейдж), `admin_create_tournament_screen.dart` (+ форма редактирования)
  (блок настроек), `utils/tournament_navigation.dart` (хелпер открытия),
  `l10n/*.arb` → `app_localizations*` (строки), провайдер регистрируется в
  `main.dart`.

**Бэкенд (Laravel, репозиторий `padel`):**
- Миграция: таблица сообщений (`tournament_id`, `user_id`, `text`,
  `created_at`) + `last_read` (`tournament_id`, `user_id`, `last_read_message_id`)
  + поля турнира `chat_enabled`, `chat_write_mode`.
- Контроллер с 4 методами + сериализация блока `chat` в ресурсе турнира.
- Проверки прав на сервере (403/422).
- Коммит + пуш бэкенда сразу после правки (правило проекта), миграции
  деплоить через `--path=` к конкретному файлу.

## 8. Явно вне области первого этапа (YAGNI)

- Вложения (фото/PDF) в сообщениях.
- Push-уведомления о новых сообщениях.
- Бейдж непрочитанных на карточке турнира в списке (сейчас — только на экране
  турнира; данные в API-контракте уже заложены, добавить визуал легко потом).
- Реакции, ответы (reply), редактирование сообщений, жалобы, «сообщение удалено»-
  плейсхолдер, typing-индикаторы, ручное архивирование чата админом.

## 9. Открытые вопросы для бэкендера

- Лимит длины сообщения (`text`) — предложение: 2000 символов.
- Размер страницы истории — предложение: 50.
- Нужен ли rate-limit на отправку (антиспам) — на усмотрение бэка.
